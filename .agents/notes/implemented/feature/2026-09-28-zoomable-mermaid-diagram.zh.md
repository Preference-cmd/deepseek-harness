# Agent Note: 可缩放的 Mermaid 图表容器

Status: implemented

[English](2026-09-28-zoomable-mermaid-diagram.md) | 中文

## Problem

一个已落定的 ```mermaid 围栏以 `max-width: 100%` 内联渲染，外层包一层 `overflow-x: auto`。于是比消息列更宽的图表只能靠横向滚动条抵达：读者无法放大时序图或类图的标签，也没有任何办法平移到已经被列裁掉的那块区域。文档站已经为自己的图表解决了这个问题——每张图一个触发按钮，打开全视口的 Panzoom 界面——但产品客户端没有对应物，而且两边无法共用代码：站点的那套住在 `website/.vitepress/theme/`，应用 bundle 并不引入它。

## Decision

客户端把已落定的图表包进一个按宽度适配的框，框上带缩放工具栏。`@panzoom/panzoom`——已经是文档站的工作区依赖、也是它那个查看器背后的库——负责变换，于是指针拖拽、双指缩放、以焦点为心的滚轮缩放与尺度钳制都是该库有测试的行为，而不是手写的指针数学。

适配尺度把图表收进画布宽度，并以图表自身尺寸封顶，因此小图不会被放大；该适配同时是 `minScale`，所以缩小就停在未缩放围栏原本呈现的视图上，复位控件也回到那里。`maxScale` 取 4，即库的默认值。画布预留的是**适配后**的高度，因此缩小后的图表下方不会留出空带。

框自己拥有边框、工具栏与画布高度；Panzoom 只拥有 paper 元素上的变换。这个切分是有承重作用的：Panzoom 以命令式写 `style.transform`，若同一个 React 元素还带 `style` prop，两者会互相覆盖。

Panzoom 把指针拖拽绑在 paper 的父元素上，却完全不绑滚轮——文档站的查看器自己接了一个正是因此。客户端也接一个，但以 Ctrl 或 ⌘ 为门槛。读者的光标通常停在消息流上，所以光标经过图表时的普通滚轮必须继续滚动对话；要求修饰键沿用浏览器与设计工具的 Ctrl+滚轮约定，而触控板捏合本来就以带 ctrlKey 的滚轮事件送达。

工具栏浮在框的右上角，悬停或聚焦时显现，因此转录流不会为每张图常驻一条控件带。它的三个控件都是纯图标，各带一个 `Tooltip`，当前尺度就显示在旁边。

## Alternatives considered

**手写 `transform: scale()`，只做步进与拖拽。** 否决：它更小，但拖拽平移与焦点缩放恰是棘手部分，除了本仓库手写的测试外不会有别的覆盖，而仓库已经为同一类内容交付了一个受维护的现成实现。

**照搬文档站的全视口模态。** 否决：它不回答这次的问题——问题是在转录流里要一个可缩放的容器。对手机尺寸的窗口它仍是更好的答案，而站点保留着它。

**像模态查看器那样接管不带修饰键的滚轮。** 否决：查看器位于已锁滚动条的全屏对话框里，页面滚动本就被关掉了。在转录流里接管裸滚轮会破坏长对话的滚动。

**沿用 `max-width: 100%` 加滚动条，只加缩放工具栏。** 否决：工具栏就得去改 SVG 自身宽度而非变换，于是每一步都会重排消息列并重置读者的滚动位置。

**只读 Panzoom 的 `panzoomchange` 事件、不保留状态。** 否决：该事件从 `requestAnimationFrame` 回调里派发，读数会比按钮按下晚一帧。视口把适配尺度保留在状态里、并在该事件上更新，对一个带动画的控件来说就是一帧延迟。

## Consequences

- `MarkdownLabels` 新增必填的 `mermaid` 字段，于是每个构造该对象的属主都要对它编译：聊天视图、文档预览侧栏、工具视图、轨迹表、计划预览、提问器、agent-preset 指南对话框，以及测试夹具。
- `IconZoomInOutlineRegular`/`Medium` 与 `IconZoomOutOutlineRegular`/`Medium` 是共享图标集里的新字形，按常规与中等描边宽度画在 16 网格上。新字形需要设计评审；最接近的现有字形（refresh、fullscreen）并不表示「放大」「缩小」，所以是新增而不是替换。
- `@panzoom/panzoom` 没有 `exports` 映射，Node 解析会落到它的 CommonJS `main`，默认导入到达时是一个命名空间对象。`thread-safe` 测试项目把它 inline，让 Vite 取 `module` 构建——浏览器 bundle 与站点本来就在用它。
- `mermaid-diagram` web e2e 的黄金基线记录消息列的可访问性树，因此新工具栏按钮会出现在其中；该场景仍断言两个已落定围栏渲染为内联 SVG。
- headless 与纯 API 界面不受影响：它们从不加载网页客户端，主机端工具仍只返回围栏源码。
